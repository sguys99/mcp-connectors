Design review

MCP 서버 개발자가 매일 켜 둘 화면을 고릅니다

세 시안은 같은 토큰 구조 위에서 Dashboard, Inspector, Chat 세 화면과 Phase 5 기능까지 배치했습니다. 이 페이지는 무엇을 고를지, 또는 무엇을 섞을지 정하는 데 필요한 근거만 모았어요.

결정할 것은 네 가지입니다

  1. 앱 셸 하나내비 위치, 사이드바, 상태바, 모바일 내비. 섞을 수 없고 하나로 정해야 합니다.
  2. 화면 세 개의 출처Dashboard, Inspector, Chat을 각각 A, B, C 중 어디에서 가져올지 고릅니다.
  3. 브랜드 색과 서체A 청록, B 인디고, C 앰버. 서체와 라운드는 색과 한 묶음으로 따라옵니다.
  4. 기본 테마처음 열 때 다크로 시작할지, 시스템 설정을 따를지 정합니다.

Comparison

항목별 비교

점수는 세 시안 중 어느 쪽이 유리한지를 나타내는 상대 평가입니다. 근거는 각 시안 제작자의 자기 평가와 update-plan 3.2의 완료 기록이며, 측정값이 아닙니다.

A Console B Studio C Workbench 5칸 = 세 시안 중 가장 유리, 진한 숫자 = 해당 항목 최고점

Phase 4 구현 비용은 칸이 많을수록 비용이 낮다는 뜻입니다. 항목 합계는 내지 않았습니다. 이 제품에서 어떤 항목이 더 중요한지에 따라 결론이 달라지기 때문이에요.

Strengths and weaknesses

시안별 장점과 약점

각 시안을 만든 담당자가 남긴 평가를 줄이지 않고 옮겼습니다. 약점도 그대로 적었습니다.

A Console

IDE형 개발자 도구. VS Code, Postman 감성

장점

  • 반복 호출과 디버깅이 가장 빠릅니다. 도구 선택, 실행, 결과, JSON-RPC 원문, 기록 재실행이 한 화면에 있습니다.
  • 키보드만으로 조작합니다. ⌘K 팔레트, ⌘↵ 실행, Esc 취소, ⌘J 패널, / 필터.
  • 밀도가 높아 Phase 5 기능을 다 넣어도 버팁니다.
  • 다크 우선과 청록 상태바로 정체성이 분명합니다.

약점

  • 첫인상과 온보딩이 약하고 크롬이 많습니다.
  • Chat을 IDE 틀에 넣어 몰입감이 C보다 낮습니다.
  • 모바일에서 툴바, 세그먼트, 탭바, 상태바가 쌓여 내용 영역이 좁습니다.
  • 1024~1280px 폭에서 빠듯합니다.

참고: 오프라인 예시 서버를 NL2SQL 데모 유지를 위해 mock-repo-mcp로 두었습니다. 서버 측 가드레일 메시지는 EN 모드에서도 원문을 유지합니다. 클릭 테스트 35건 통과.

B Studio

깔끔한 SaaS 제품. Linear, Vercel 감성

장점

  • 첫인상과 온보딩이 가장 좋습니다. Getting started 4단계 체크리스트와 선화 빈 상태가 있습니다.
  • 역할별로 면을 나눠 위계가 잘 읽힙니다.
  • shadcn과 기존 Geist에 거의 1:1로 대응해 Phase 4 비용이 낮습니다.
  • 다크도 면 단계와 상단 하이라이트로 따로 설계했습니다.

약점

  • 넓은 여백 탓에 Inspector가 세로 스크롤을 요구하고, 한 화면의 요청과 응답 정보량이 A보다 적어 반복 디버깅이 느립니다.
  • Chat의 도구 추적이 스레드 인라인이라 C보다 흐름 파악이 약합니다.
  • 같은 높이 카드 그리드라 HTTP 필터를 걸면 2행에 빈 공간이 생깁니다.
  • 모바일 Inspector 헤더가 첫 화면의 1/3을 차지합니다.

참고: 요약 지표는 타일 대신 한 줄 문장입니다. 모바일은 하단 탭바와 Inspector 3단계 흐름. 클릭 테스트 31건 통과.

C Workbench

대화와 실행 추적 중심. LangSmith, Claude Console 감성

장점

  • LLM과 도구의 상호작용을 시간축으로 읽습니다. 어디서 시간이 쓰였는지, 반복별 토큰 누적, 어느 가드레일이 막았는지 보입니다.
  • Chat, Inspector, Dashboard가 워터폴 컴포넌트 하나를 공유해 학습 비용이 낮습니다.
  • 승인 대기와 거부가 타임라인에 남아 감사와 디버깅에 유리합니다.
  • 라이트와 다크의 완성도가 같습니다.

약점

  • 3열 구성이 1280px 미만에서 빡빡합니다. 대화 목록 드로어와 워터폴 폭 축소가 필요합니다.
  • 밀도가 A보다 낮아 Inspector 반복 단건 호출에 스크롤이 더 필요합니다.
  • 앰버가 라이트에서 면 색으로 약해 브랜드 존재감이 낮습니다.
  • 실제 SSE 이벤트를 시간 정보가 있는 스팬으로 바꾸는 Phase 4/5 구현 비용이 큽니다.

이슈: Claude Desktop HTTP 설정은 npx mcp-remote 브리지를 가정했습니다(Phase 5 전 확인 필요). Atkinson Hyperlegible Mono의 한국어 폴백 간격이 고르지 않습니다.

고정

잘 섞이는 조합

  • BB의 Getting started 체크리스트를 A나 C의 Dashboard 위에 얹기. 체크리스트는 독립 카드라 셸을 가리지 않습니다.
  • CC의 워터폴을 A의 Chat 우측 추적 패널로. A의 터미널형 텍스트 추적과 같은 자리이고, 순서에 시간 비중까지 더해집니다.
  • AA의 명령 팔레트와 단축키(⌘K, ⌘↵, Esc)는 어느 셸에도 붙습니다.
  • AA의 JSON-RPC 도킹 로그를 B Inspector의 Response 탭 옆으로. B에도 로그 탭이 있어 자리만 옮기면 됩니다.
  • B색만 다른 시안에서 가져오기. 예를 들어 A 레이아웃에 B 인디고와 Geist를 쓰면 Phase 4에서 기존 Geist를 그대로 씁니다.

섞을 때 주의할 점

  • !셸은 하나. 화면을 다른 시안에서 가져오면 그 화면을 고른 셸의 콘텐츠 영역에 맞춰 다시 배치해야 합니다.
  • !C 워터폴의 LLM 스팬은 브랜드 색, 도구 스팬은 청록입니다. A 청록과 함께 쓰면 두 스팬이 비슷해지므로 도구 스팬 색을 바꿔야 합니다.
  • !C 앰버는 라이트에서 버튼 면 대비가 1.82입니다. 글자 없는 상태 표시에는 --brand-text를 써야 합니다.
  • !Inspector와 Chat을 다른 시안에서 가져오면 응답 블록과 도구 카드 모양을 한쪽 기준으로 맞춰야 합니다. 두 화면의 일체감이 이 제품의 차별점입니다.
  • !C Chat의 3열(대화 목록, 대화, Trace)을 A 셸에 넣으면 사이드바와 대화 목록이 겹칩니다. 대화 목록을 A 사이드바로 합치세요.
추천

A 셸 기반 혼합안: A Inspector + C 워터폴 Chat + B 온보딩

근거

  1. 매일 켜 두는 도구라면 반복 속도가 먼저입니다. 서버 개발자가 가장 자주 하는 일은 도구를 고치고 다시 호출하는 것이고, 이 항목에서 A가 가장 유리합니다. 밀도가 높아 Phase 5 기능을 다 넣어도 버팁니다.
  2. 차별점은 Inspector + Chat 일체형입니다(update-plan 7.1). 공식 MCP Inspector에 없는 것은 LLM 도구 사용 루프이고, 그 루프를 가장 잘 보여 주는 것이 C의 워터폴입니다. 같은 셸 안에서 Inspector 응답과 Chat 추적이 한 어휘를 쓰면 일체형이라는 주장이 화면으로 증명됩니다.
  3. A의 가장 큰 약점은 첫인상인데, 컴포넌트로 메울 수 있습니다. B의 Getting started 체크리스트는 독립 카드라 A Dashboard 위에 그대로 얹힙니다. 처음 실행할 때만 보이고 숨길 수 있게 하면 매일 쓰는 사람에게 방해가 되지 않아요.
  4. 기본 테마는 시스템 따름을 권합니다. 오픈소스 사용자는 환경이 제각각입니다. A의 다크 값은 그대로 두고 처음 열 때 강제하지만 않습니다.

대가와 조건

  • Phase 4 비용은 B 단독안보다 큽니다. IDE 셸, 리사이즈 패널, 명령 팔레트를 새로 만들어야 합니다.
  • 워터폴은 단계적으로 가는 편이 안전합니다. Phase 4에서는 도구 호출 단위 스팬만 그리고, 반복별 토큰과 승인 대기 스팬은 Phase 5(5-C)에서 붙이는 방식입니다.
  • A 청록과 C의 도구 스팬 청록이 겹치므로 도구 스팬 색을 다른 색조로 바꿔야 합니다.
  • 모바일은 A의 약점으로 남습니다. 셸을 정할 때 모바일 내비만 B의 하단 탭바 방식으로 바꾸는 안을 함께 검토해 주세요.

대안: 공개 직후의 첫인상과 구현 속도가 가장 중요하다면 B 셸 중심안도 합리적입니다. B Dashboard와 B Inspector를 쓰고 Chat 오른쪽에 C 워터폴 패널만 더하는 구성입니다. 반복 디버깅 속도는 A안보다 느립니다.

Your pick

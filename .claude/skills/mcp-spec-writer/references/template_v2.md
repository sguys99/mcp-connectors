## 1. 개요

### 1.1 서버명 / 한 줄 소개

📝 **작성 가이드**
MCP 서버의 식별 가능한 코드명과, 무엇을 하는 서버인지 한 줄로 설명합니다.

💡 **예시**
- **서버명**: `code-repo-mcp`
- **한 줄 소개**: 내부 Git 저장소와 코드리뷰 Agent를 연동하여 PR/Commit/파일 조회 및 영향도 분석을 지원하는 MCP 서버

### 1.2 목적 및 배경

📝 **작성 가이드**
- **목적**: 이 MCP 서버를 왜 만드는가
- **배경**: 현재 어떤 문제/한계가 있는가
- **기대 효과**: 만들고 나면 무엇이 좋아지는가 (가능하면 정량적으로)

💡 **예시**
- **목적**: 코드리뷰 Agent가 내부 저장소의 변경 이력/PR/파일 정보에 자동으로 접근하여 리뷰 품질과 속도를 향상
- **배경**: 현재 리뷰어가 PR을 수동으로 열어 변경 영향도를 파악하느라 PR당 평균 30분 이상 소요
- **기대 효과**: PR당 리뷰 소요시간 30% 단축, 영향도 분석 누락 건수 감소

## 2. 범위

### 2.1 포함 범위 (In-Scope)

📝 **작성 가이드**
이 MCP가 제공할 기능을 명확히 나열합니다. "어떤 시스템과 연동해서 어떤 작업을 지원하는지"가 보여야 합니다.

💡 **예시**
- 내부 저장소의 PR / Commit / File / Branch 정보 **조회**
- 변경된 파일 목록 및 diff 추출
- 특정 파일을 참조/의존하는 파일 목록 제공 (영향도 분석 보조)

### 2.2 제외 범위 (Out-of-Scope)

📝 **작성 가이드**
"이것도 해주겠지" 하고 오해할 수 있는, 그러나 본 MCP가 처리하지 **않을** 부분을 명시합니다.

💡 **예시**
- PR Merge / Approve / Close 등 **쓰기 작업** (보안상 제외)
- 코드 리뷰 결과의 생성 자체 (Agent의 책임 영역)
- 내부 저장소 외 타 저장소(GitHub 등) 연동

## 3. 사용자 및 주요 시나리오

### 3.1 사용 Agent

📝 **작성 가이드**
본 MCP를 호출하는 Agent와 호출 패턴을 적습니다. 호출 빈도는 용량 산정의 근거가 됩니다.

💡 **예시**
- **호출 주체**: 코드리뷰 Agent
- **호출 빈도**: 1일 약 200회, 피크 시간대 분당 10회
- **호출 성격**: 읽기 위주 (조회 100%)

### 3.2 주요 사용 시나리오 (Use Cases)

📝 **작성 가이드**
Agent가 본 MCP를 어떻게 사용할지 대표 시나리오 2~3개를 한두 줄로 요약합니다. 이 시나리오가 곧 5장 Tool 설계의 근거가 됩니다.

💡 **예시**

| ID | 시나리오 | 사용 Tool (5장과 매핑) |
|---|---|---|
| UC-01 | PR ID를 받아 변경된 파일 목록과 diff를 조회하여 영향 모듈을 분석한다 | `get_pr`, `get_file_diff` |
| UC-02 | 특정 파일을 참조하는 다른 파일/모듈 목록을 조회한다 | `search_references` |

## 4. 시스템 구성

### 4.1 MCP 서버

📝 MCP 서버의 배포 방식과 전송 방식. Transport는 호스팅, 인증, 네트워크 설계의 전제입니다.

💡 **예시**

| 항목 | 내용 |
|---|---|
| Transport | Streamable HTTP |
| 배포 환경 | 내부 Kubernetes 클러스터 |
| 엔드포인트 | `https://code-repo-mcp.example.internal/mcp` |
| MCP SDK | Python FastMCP |
| 사용 프리미티브 | Tools 사용 / Resources, Prompts 미사용 (사용하면 5.3에 명세) |

### 4.2 연동 백엔드 시스템
📝 **작성 가이드**
MCP가 연결할 백엔드 시스템의 정보를 적습니다. 개발자가 실제 연결을 구성할 수 있을 정도로 구체적이어야 합니다.

💡 **예시**

| 항목 | 내용 |
|---|---|
| 시스템명 | 내부 코드 저장소 (Git 호스팅 서버) |
| 종류 | Git 기반 코드 저장소 (내부) |
| 엔드포인트 | `https://code-repo.example.internal/api/v1` |
| 프로토콜 | HTTPS (REST API) |
| 인증 방식 | Personal Access Token (PAT) |
| 네트워크 | 내부망, MCP 서버는 동일 VPC에서 직접 호출 가능 |
| 참고 문서 | 저장소 서버 API 명세서 링크 |

## 5. 기능 요구사항 (Tools)

> MCP 서버의 핵심 명세입니다. **이 장이 가장 중요**하며, Tool 개수만큼 5.2를 반복하여 작성합니다.

### 5.1 Tool 목록 (요약)

📝 **작성 가이드**
제공할 Tool을 한눈에 볼 수 있도록 표로 요약합니다. Hint 칼럼(`readOnly`/`destructive`/`idempotent`)은 MCP 표준 annotation으로, 클라이언트가 확인 다이얼로그 등 UX를 결정할 때 사용합니다. 각각 Boolean으로 표기합니다.

💡 **예시**

| Tool ID | Tool Name | 설명 | readOnly | destructive | idempotent |
|---|---|---|---|---|---|
| T-01 | `get_pr` | PR ID로 PR 메타데이터 조회 | true | false | true |
| T-02 | `get_file_diff` | PR 내 특정 파일의 변경 diff 조회 | true | false | true |
| T-03 | `search_references` | 특정 파일을 참조하는 파일 목록 조회 | true | false | false |

### 5.2 Tool 상세 명세

📝 **작성 가이드**
> ⚠️ **LLM Description은 이 의뢰서에서 가장 중요한 항목**입니다.
> Agent가 언제 이 Tool을 호출할지 결정하는 유일한 단서이므로, 사람용 한 줄 설명과 **분리하여** 작성해야 합니다.
각 Tool마다 아래 항목을 채웁니다. 개발자가 보고 바로 구현할 수 있을 정도의 정밀도가 목표입니다.
- **설명**: Tool이 무엇을 하는지
- **입력**: 파라미터명, 타입, 필수 여부, 설명
- **출력**: 반환 JSON 구조 (예시로 보여주는 게 가장 명확함)
- **주요 에러**: 어떤 상황에서 실패하는지

#### ▶ T-01 `get_pr`

- **설명**: PR ID로 PR 메타데이터와 변경 파일 목록 반환

- **LLM Description** (Tool에 노출되는 본문, 3~7줄)
```
  PR의 메타데이터(제목, 작성자, 상태)와 변경 파일 목록을 조회한다.
  PR 단위 요약 정보가 필요할 때 사용.
  특정 파일의 변경 내용까지 보려면 get_file_diff를 추가 호출할 것.
  파일 본문 전체가 필요한 경우에는 사용하지 말 것.
  호출 예: "PR 1234의 변경 요약 확인" → get_pr(pr_id="1234")
```

- **입력 파라미터**

  | 파라미터 | 타입 | 필수 | description (LLM 노출) |
  |---|---|---|---|
  | `pr_id` | string | Y | PR 식별자. 숫자 문자열, 접두사 없음 (예: `"1234"`) |

- **출력 예시 (JSON)**
  ```json
    {
      "pr_id": "1234",
      "title": "Refactor auth module",
      "status": "open",
      "files_changed": [
        { "path": "src/auth/login.py", "change_type": "modified" }
      ]
    }
  ```

- **빈 결과**: `files_changed: []` (PR은 존재하나 변경 파일이 없는 경우)

- **응답 크기 제어**: `files_changed`는 최대 200건, 초과 시 `cursor` 반환

- **에러 응답** (코드만이 아닌 **자연어 원인 + 조치** 포함)

  | 코드 | 메시지 예시 |
  |---|---|
  | `PR_NOT_FOUND` | "PR 1234를 찾을 수 없습니다. pr_id는 숫자 문자열이어야 합니다." |
  | `ACCESS_DENIED` | "해당 PR에 대한 조회 권한이 없습니다. Agent 권한을 확인하세요." |


> ※ T-02, T-03 ... 각 Tool에 대해 위 블록을 복제하여 작성

### 5.3 Resources / Prompts (선택)

📝 **작성 가이드**
4.1 "사용 프리미티브"에 Resources나 Prompts를 쓴다고 적었을 때만 둡니다. 쓰지 않으면 이 절을 통째로 뺍니다. Resource는 애플리케이션이 읽는 데이터(URI로 식별, `{param}`이 있으면 template), Prompt는 사용자가 고르는 메시지 템플릿입니다. 구현 예시는 저장소의 `src/mcp-servers/starter_mcp/primitives.py`입니다.

💡 **예시**

| 종류 | URI 또는 이름 | MIME type / 인자 | 설명 (LLM 노출) |
|---|---|---|---|
| Resource | `code-repo://schema` | `application/json` | 이 서버가 제공하는 도구와 응답 필드 요약 |
| Resource template | `code-repo://repos/{repository_id}/readme` | `text/markdown` | 저장소 README 본문 (외부 텍스트, 신뢰 경계 적용) |
| Prompt | `review_session` | `language` (필수) | 지정 언어 코드 리뷰를 시작하는 메시지 묶음 |

## 6. 비기능 요구사항

### 6.1 성능

📝 **작성 가이드**
"빠르게"가 아닌 **측정 가능한 수치**로 적습니다. 응답 크기는 바이트뿐 아니라 **토큰 관점**에서도 제약해야 합니다 (LLM 컨텍스트 윈도 보호).

💡 **예시**
- P95 응답시간 < 2초
- 동시 5건 처리 가능
- 단일 응답 payload 최대 1MB

### 6.2 보안

📝 일반적인 인증/시크릿 외에, MCP 특유 위협(간접 prompt injection)과 인가 경계를 명시.

💡 **예시**
- **MCP 인증**: Agent별 API Key, 헤더 전달
- **백엔드 자격증명**: 저장소 PAT는 Vault에서 주입, 평문 노출 금지
- **인가 경계**: 호출자 Agent의 권한 범위 내 데이터만 반환 (공용 PAT로 권한 우회 금지)
- **간접 injection 방어**: 응답에 포함되는 외부 텍스트(PR 본문, 코멘트 등)는 별도 필드로 격리하여 Agent가 신뢰 경계를 인식할 수 있도록 함
- **민감정보**: 사번 등 내부 식별자 마스킹

### 6.3 로깅

📝 **작성 가이드**
운영 추적과 장애 분석을 위해 남길 항목을 적습니다.

💡 **예시**
- 항목: 호출 시각, Agent ID, Tool명, 입력 파라미터 해시, 응답 시간(ms), 결과 코드
- 보존 기간: 90일
- 수집 시스템: 내부 Splunk

## 7. 에러 처리

📝 **작성 가이드**
MCP에서 에러는 **Agent가 다음 행동을 결정할 수 있는 형태**여야 함. 코드만 반환하지 않고 자연어 원인+조치를 함께 포함.

💡 **예시**

| 분류 | 처리 |
|---|---|
| 입력/권한 오류 | `isError: true` + 원인과 조치를 포함한 자연어 메시지 |
| 백엔드 오류 | `isError: true` + 재시도 가능 여부 명시 |

- 백엔드 호출 Timeout: 5초
- 재시도: 백엔드 5xx 발생 시 1회 재시도 (Exponential Backoff)

## 10. 인수 기준 (Acceptance Criteria)

📝 **작성 가이드**
"이 조건을 모두 만족하면 인수한다"는 체크리스트입니다. 모호한 표현 대신 본 문서의 각 장을 참조하는 형태로 적으면 분쟁이 줄어듭니다.

💡 **예시**

- [ ] **LLM Tool-calling 평가셋 통과율 ≥ 90%**
